DIP mobile security architecture

A review of the two CLAUDE.md files for the Android app and the DMZ web app: what they require, drawn as pictures, what in them needs fixing or deciding, and how far the DIP Field Service app as deployed today (zApps → mApps) is from them.

Sound

Three separate proofs on every call (device certificate, user token, app integrity), the user tied to the device, fail-closed checks, and a DMZ that holds no data or database.

Must fix in the documents

They assume Azure (App Gateway, App Service, managed identity), but DIP's DMZ is on premises. They also ban on-phone data, which offline field work needs.

Decide before building

Play Store or sideloading. Whether every reader has an Entra account. Where nonces and sessions are kept, given the DMZ may have no database.

Review of the documents

Findings

The controls themselves are good. The issues below are places where the documents conflict with DIP's setup or with each other, or leave a gap.

HIGH · H1

They assume Azure, but DIP's DMZ is on premises

Both files rely on App Gateway header rewrites, App Service private endpoints, a site-to-site VPN and managed identity. zApps runs on an IIS server in DIP's own DMZ, which has none of these. Managed identity in particular does not exist outside Azure.

Decide the hosting first. If it stays on premises, rewrite §3.1 and §3.6: IIS (or Kestrel) requires the client certificate itself and the app reads it from the connection, so no headers to trust; the DMZ authenticates to the internal app with its own client certificate, as zApps already does.

HIGH · H2

"No business data on disk" conflicts with offline field work

Android §3.7 allows data in memory only. Meter readers and inspectors work where there is no signal, so readings, photos and inspection drafts have to wait on the phone until it can send them. Under §3.7 that work would be lost.

Add a written exception: queued work is kept encrypted with a non-exportable Keystore key (as the app does now), deleted once the server confirms it, deleted on sign-out or certificate removal, and never older than N days.

HIGH · H3

Play Integrity needs the Play Store, but the APK is sideloaded

The documents flag this themselves. Today the app is installed from a GitHub release APK, so the app-recognition verdict would not be PLAY_RECOGNIZED. Every phone would then fail attestation, or the server would have to loosen the check.

Publish through a closed testing track in Google Play before building §3.6. If that is not possible, use device integrity only and say so in the documents.

HIGH · H4

The certificate checks trust headers that a caller could send

Checking that the PEM matches the fingerprint does not stop forgery, because both headers come from the same source. The checks are only safe if (a) nothing but App Gateway can reach the DMZ app, and (b) App Gateway overwrites any X-Client-Cert* header the client sent. Point (b) is not written anywhere and is outside this repository.

Put (b) in the infrastructure requirements, and add an end-to-end test that sends forged headers through App Gateway and expects 403.

MED · M1

The private key is made by IT and travels as a file

The .p12 and its password go to the user by e-mail, WhatsApp or similar. Copies stay in mailboxes and backups, and the "delete the file" step cannot be checked.

Have the app generate the key in the Keystore (StrongBox where the phone has it) and send a certificate request. IT signs it after approving the device. The key never leaves the phone and no password has to be sent.

MED · M2

Every user must have an Entra account

Mandatory Entra sign-in, with the token's user matching the certificate's e-mail, means each reader needs their own Entra account, a licence and MFA on a personal phone. It also means one phone per person. The current app uses a registered phone plus a chosen reader (FR-002) to avoid exactly this.

Confirm with HR and IT that every field user is in Entra. If not, keep device mode for them and document the exception.

MED · M3

Nonces and sessions need storage, but the DMZ may have no database

Nonces (2 min) and attested sessions (12 h) are stored server-side. Kept in memory, they are lost on every restart, and they break as soon as App Service runs a second instance.

Run a single instance and accept re-attestation after a restart, or keep these records in the internal app behind a small internal endpoint.

MED · M4

The 64 KB body limit and 60-a-minute rate limit are too small for field sync

A photo can be up to 2 MB and an inspection visit up to 512 KB. A phone that comes back online with a day's queue sends well over 60 requests a minute.

Name the larger limits per route in §3.5, as zApps already does (64 KB JSON, 512 KB visit, 2.1 MB photo). Rate-limit uploads separately from reads.

MED · M5

Pinning a public CA's intermediate can take every phone offline

Public CAs change their intermediates. With a sideloaded app that cannot be updated quickly, a renewal that switches intermediate cuts off all users at once.

Pin the CA's root plus a second CA's root as the backup, and agree with whoever renews the zApps certificate that they check the pins first.

LOW · L1

The business endpoints are "to be defined" in both files

They already exist: readings, photos, meter lists, the inspection plan and visits. The list is in gateway/src/MeterReading.Gateway/Routes.cs.

Copy that list into §5 of the DMZ file and §6 of the Android file, so reviewers can check one against the other.

LOW · L2

Pipeline and fingerprint details

Both files name Azure DevOps, but the code and APK builds are on GitHub Actions. The SHA-1 fingerprint is fine as an identifier but not for security.

Name the real pipeline. Compare SHA-256 of the certificate in the app itself, and look up the registry by SHA-256.

Next

Decisions needed, in order

  1. Hosting: Azure App Gateway and App Service as written, or the on-premises zApps already running? Most of the other rewrites depend on this answer (H1).
  2. Distribution: a Google Play closed track or a sideloaded APK? This decides whether Play Integrity can be used at all (H3).
  3. Users: does every field user have an Entra account with MFA? If yes, Entra sign-in replaces "reader chosen on the phone" (M2).
  4. Offline exception: approve the encrypted offline queue, with its deletion rules (H2).
  5. Device certificate: made on the phone with a signing request, or a .p12 issued by IT (M1)?

Once these are settled, the work can go in the small steps both files ask for: certificate onboarding and mTLS first, then pinning, then Entra, then attestation. The device key stays in place until each step is live.
